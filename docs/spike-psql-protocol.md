# Spike: протокол взаимодействия с psql

Дата: 2026-11-13. Статус: завершён, решение по движку подтверждено с четырьмя поправками.

## Окружение

- Сервер: `postgres:18` (PostgreSQL 18.7, Debian 18.7-1.pgdg13+2), порт `localhost:55432`, фикстуры `deploy/fixture.sql`.
- Клиент A: `psql 14.24` (Ubuntu 22.04, локальный).
- Клиент B: `psql 18.7` (тот же контейнер, запуск через `docker compose exec`).
- Проба: `docs/spike/probe.py`, 24 кейса, отчёты в `/tmp/psql-tui/probe-{host,psql18}.json`.

Воспроизведение:

```sh
docker compose -f deploy/docker-compose.yml up -d
printf '127.0.0.1:55432:appdb:postgres:spikepass\n' > /tmp/psql-tui/probe.pgpass
chmod 600 /tmp/psql-tui/probe.pgpass
PGPASSFILE=/tmp/psql-tui/probe.pgpass python3 docs/spike/probe.py \
    --tag host --conn 'postgresql://postgres@127.0.0.1:55432/appdb'
```

## Вердикт

Живой процесс `psql -X -q --csv` годится как движок: границы запросов, коды ошибок, счётчики строк и CSV-экранирование работают предсказуемо. Переход на libpq-драйвер не нужен.

Но контракт из спецификации нужно поправить в четырёх местах:

1. `SIGINT` для отмены запроса использовать нельзя — он убивает psql вместе с сессией.
2. Проверка полноты statement на клиенте обязательна: незакрытая скобка превращает сессию в чёрную дыру.
3. `NULL` и пустая строка неразличимы после разбора CSV — нужен `-P null=<sentinel>`.
4. `COPY ... TO STDOUT` и `COPY ... FROM STDIN` должны отклоняться на клиенте.

Плюс два уточнения: `stderr` асинхронен относительно маркера, а `.pgpass` с неверными правами игнорируется молча.

Поведение клиентов 14.24 и 18.7 на всех сравнимых кейсах совпало: различий по маркеру, CSV, `\gdesc`, `FETCH_COUNT` и `:ROW_COUNT` не обнаружено. Требование «psql 14+» остаётся валидным; для работы с серверами 18+ рекомендуем psql той же major-версии.

## Результаты по кейсам

| Кейс | Результат | Следствие |
|---|---|---|
| `-q` и command-tag | DDL/DML дают 0 записей, теги `CREATE TABLE`/`INSERT 0 3` в stdout отсутствуют | `-q` обязателен, как и предполагалось |
| `:ROW_COUNT` | `INSERT` 3 → `3`, `SELECT` 3 строки → `3`, DDL → `0` | счётчик строк берём из маркера |
| CSV и «пыточные» значения | все 14 значений (запятая, кавычка, LF, CRLF, таб, кириллица+emoji, backslash, `\|`, `;`, строка вида маркера, 5000 символов) вернулись байт-в-байт | `encoding/csv` достаточно, построчный разбор не нужен |
| `NULL` vs `''` | в сыром виде `NULL` — пустое поле без кавычек, `''` — `""`; после CSV-парсера оба становятся `""` | нужен `-P null=␀NULL␀` |
| `-P null=␀NULL␀` | `␀NULL␀,` — NULL помечен, пустая строка осталась пустой | решение принято |
| `bytea`, `numeric` | `\xdeadbeef`; 30 цифр до запятой и 9 после сохранены | типы не теряются, округления нет |
| Синтаксическая ошибка | 0 записей, `:ERROR=true`, `:SQLSTATE=42601`, сессия жива, следующая команда работает | ошибки отделимы от результата |
| Ошибка прав | `:SQLSTATE=42501`, сессия жива; разрешённый объект читается тем же пользователем | «нет прав» — нормальный результат |
| NOTICE / WARNING | только в stderr, в stdout ничего | панель Messages |
| Пустой результат | ровно один заголовочный рекорд | «0 строк» распознаётся |
| Несколько statement в одной записи | два набора результатов, один маркер, `:ROW_COUNT` от последнего | нужен клиентский сплиттер |
| Statement с `;` + наша `;` | пустой statement не даёт лишних записей | можно всегда дописывать `;` |
| `FETCH_COUNT=2` на 5 строк | 6 записей: заголовок один раз, 5 строк | батчевая выдача в UI возможна |
| `\gdesc` | `Column|Type`, `a|integer`, `b|timestamp with time zone`, без выполнения запроса | типы колонок доступны, если понадобятся |
| `\r` | сбрасывает query buffer, сессия восстанавливается | аварийное восстановление |
| Потеря соединения (`pg_terminate_backend`) | stdout закрывается, psql выходит с кодом 2 | потеря связи детектируется |
| `PGPASSFILE` 0600 | подключается | путь для пароля подтверждён |
| `PGPASSFILE` 0644 | молча игнорируется, `fe_sendauth: no password supplied`, без предупреждения | права надо проверять самим |
| Без passfile и без tty | exit 2, `fe_sendauth: no password supplied` | ошибка вместо зависания |
| `SIGINT` во время `pg_sleep` | запрос отменён (`Cancel request sent`, `57014`), но psql **умер** с кодом 3 | отмена через SIGINT запрещена |
| `pg_cancel_backend(pid)` из одноразового psql | `57014`, сессия жива, следующая команда работает, 1.03 с | принятая схема отмены |
| То же под ролью без суперправ | работает | отмена не требует привилегий |

## Что ломается и почему это важно

### Незакрытая скобка делает сессию чёрной дырой

`psql` считает глубину скобок. На `SELECT (1;` он не отправляет запрос на сервер, а продолжает копить буфер. Дальше воспроизводимо:

- следующий statement (`SELECT 2;`) тоже уходит в буфер и не выполняется;
- `\echo`-маркер печатается, но `:ERROR`, `:SQLSTATE`, `:ROW_COUNT` остаются **неподставленными** — литерально `|:ERROR|:SQLSTATE|:ROW_COUNT`;
- закрывающая `)` отдельной строкой буфер не сбрасывает;
- восстанавливает только `\r`.

То есть по маркеру видно, что что-то не так (литеральные `:ERROR`), но результат уже потерян: запрос не выполнялся, а следующий запрос тоже. Единственная надёжная защита — не отправлять неполный statement.

### Незакрытая кавычка съедает маркер

На `SELECT 'abc` psql считает строку незакрытой и забирает в неё следующую строку вместе с `\echo`, затем сообщает `unterminated quoted string`. Маркера не будет вообще — граница запроса потеряна полностью, и различить это по stdout невозможно.

### Скомпилированный `;` не спасает, но помогает частично

Если дописывать `;` к statement без терминатора, обычные обрывы (`SELECT 1 +`) становятся ошибкой сервера с корректными `:ERROR`/`:SQLSTATE`. Не спасает это только для незакрытой скобки и незакрытой кавычки — ровно тех случаев, которые ловит грамматическая проверка на клиенте.

### COPY

- `COPY (SELECT 1 AS a, 'x,y' AS b) TO STDOUT WITH (FORMAT csv)` кладёт в stdout данные **без заголовка** и с `:ROW_COUNT=0`. Для адаптера это выглядит как валидный результат из одной строки — тихая ошибка.
- `COPY app.edge_cases FROM STDIN` съедает маркер как данные (`invalid input syntax for type integer: "echo __PGC_..."`), затем ждёт `\.` — интерфейс зависает.

Обе формы нужно отклонять в редакторе до отправки.

### stderr асинхронен

В кейсе с неполным statement маркер пришёл раньше, чем успели прочитаться строки stderr. Если строить текст ошибки только на «что успело прийти к моменту маркера», можно получить пустое сообщение при `:ERROR=true`. Нужна пауза до затишья stderr (порядка 50 мс, с ограничением сверху), а не мгновенная фиксация.

## Контракт адаптера после spike

Запуск сессии:

```
psql -X -q -w --csv -P null=␀NULL␀ -d <conninfo>
```

- `-X` — не читать `psqlrc`; `-q` — без command-tag; `--csv` — RFC 4180.
- `-P null=␀NULL␀` — единственный способ отличить NULL; поле, равное сентинелю целиком, считается NULL (совпадение с реальными данными документируется как известное ограничение).
- Пароль — только через `PGPASSFILE` (0600) или `~/.pgpass`; права проверяются самим приложением, потому что libpq молчит.
- `-w` (`--no-password`) обязателен. Без него первый коннект без пароля вешает psql на чтении с `/dev/tty` поверх интерфейса: интеграционный тест TUI получил `Password for user postgres:` и 22 секунды ожидания вместо ошибки. С `-w` psql сразу отдаёт `fe_sendauth: no password supplied`, и приложение спрашивает пароль своим модальным окном.

Один запрос:

```
<statement>;                      # statement проверен на полноту и не содержит нескольких statement
\echo __PGC_<rid>__|:ERROR|:SQLSTATE|:ROW_COUNT
```

- `<rid>` — 8 случайных hex-символов на запрос.
- Конец запроса — одиночный CSV-рекорд, начинающийся с `__PGC_<rid>__|`.
- Если в этом рекорде литерально присутствует `:ERROR` — framing сломан: отправить `\r`, отбросить результат, показать внутреннюю ошибку.
- После маркера — дочитать stderr до затишья, затем собрать `ResultSet` + `ExecutionStatus`.

Отмена:

- После подключения один раз выполнить `SELECT pg_backend_pid()` и запомнить pid.
- Отмена — не сигнал, а одноразовый `psql -X -q -tA -c 'SELECT pg_cancel_backend(<pid>)'` с теми же conninfo и passfile.
- Успех — маркер с `:SQLSTATE=57014`; сессия и следующая команда продолжают работать.

Запрещено в редакторе на MVP:

- `COPY ... TO STDOUT`, `COPY ... FROM STDIN` — явная ошибка с объяснением;
- psql backslash-команды пользователя — только служебные, генерируемые адаптером.

## Что осталось непроверенным

- Память и время на результатах в сотни тысяч строк (лимит UI пока не измерен).
- Поведение при `statement_timeout` на сервере и при обрыве сети без закрытия сокета.
- Различие «объект отсутствует» и «объект не виден» на уровне каталогов для ролей без прав.
- `\gdesc` для DDL и для `INSERT ... RETURNING`.
- PostgreSQL 19: добавить в матрицу после GA, поведение адаптера не должно зависеть от minor-версии.
